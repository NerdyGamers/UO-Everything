# UO-Everything — Software Project Roadmap

**Revision:** 2026-10-14
**Supersedes:** the 9-phase wiki-style roadmap (content-completion checklists).

## The shift

The old roadmap treated this as a writing project: finish articles, then finish more articles, then someday think about structure. A software project works the other way around: **the data model is the product, and the prose is one rendering of it.**

The progression:

```
Documentation → Enriched documentation → Structured database → AI-ready knowledge system
```

Stages gate on each other. You don't start the asset pipeline before the ID scheme is locked; you don't build RAG before the structured data validates.

## Stage 0 — Shipped (where we stand today)

No work here. This is the inventory everything else builds on.

- **Content:** 743 curated articles (lore, skills, mechanics, mobiles, items, quests, housing, locations, history, shards, community) + 31,411 per-item catalog pages. Zero broken internal links.
- **Site:** live on GitHub Pages (gh-pages branch), hash routing, per-section nav, global search over curated pages, hex-ID catalog lookup.
- **Stable IDs:** ItemID (hex, in catalog page paths) and BodyID (mobiles) already exist. This was the old critical path's first dependency — it's done.
- **Assets:** client binaries in the private asset-database repo's `client/` folder; ~13,847 PNGs (gumps, land tiles, textures, maps) extracted locally, animations + item-art zips also staged (~842 MB total in `uo-asset-staging/`). Push to the private repo via git LFS is Jar's action (tracked separately).

**Known gaps:** the 31k catalog pages are excluded from the site search index (ID lookup only); catalog pages carry decoded tile flags but no structured front matter yet.

## Stage 1 — Enriched documentation (metadata & taxonomy)

**Goal:** every page carries machine-readable metadata, and the taxonomy is a file, not a convention in someone's head.

This is the next milestone. Everything downstream hangs off the schema.

**Deliverables:**
- `schema/` — metadata schema v1 (JSON Schema): item, mobile, location, lore, mechanic, skill, quest, spell page types.
- Front-matter spec: required vs. optional fields per type (ID fields, expansion, era, categories, cross-references, image path).
- Templates: one `templates/` file per page type with commented fields.
- `taxonomy.yaml` — the controlled vocabularies: categories, expansions, eras, facets, mob taxonomies (family → species), item classifications.
- Backfill script: walks the 743 curated pages + 31,411 catalog pages, injects front matter from what can be derived (paths, tile flags, section), flags the rest for review.
- Naming convention doc: file names, ID formats (`0x0F0A` style hex), image file names keyed to IDs.

**Acceptance:** a validator passes on 100% of pages (CI, below); taxonomy changes go through a reviewed edit to one file.

**Dependencies:** none beyond a locked schema decision. Blocking for: Stage 2 image naming, Stage 3 dataset builds.

## Stage 2 — Asset pipeline (images & animations)

**Goal:** every item and mobile has a thumbnail, generated by a repeatable pipeline — not a pile of manual exports.

**Deliverables:**
- Exporter scripts (or a headless/CLI mode added to UOAssetSuite — see open decision): item art from `art.mul`/`tileart.uop`, mobile frames from animation files, gump/landtile/texture thumbnails.
- Normalization step: transparency handling, standard resolution, thumbnail sizes (e.g., 128px display, 512px detail).
- Naming: `<ItemID-hex>.png`, `<BodyID>.png`, frame variants `<BodyID>-idle.png`.
- Storage: private asset-database repo via git LFS (client-derived art stays private); public site references thumbnails by stable URL.
- Wire-up: front matter `image:` fields populated by the pipeline, not by hand.

**Acceptance:** pipeline re-runs from client files to thumbnails without manual steps; a missing-image report lists exactly which IDs have no art.

**Dependencies:** Stage 1 (ID-keyed naming). Blocked on: the LFS push of extracted assets (Jar's tracked action).

## Stage 3 — Structured data layer

**Goal:** the wiki stops being "pages with metadata" and becomes a database that *renders* pages.

**Deliverables:**
- SQLite database as the source of truth for structured entities (items, mobiles, skills, spells, locations) — populated from validated front matter + client data (tiledata, art index, animation tables).
- Dataset builds: `datasets/items.json`, `mobiles.json`, `locations.json` (and `.csv` equivalents), generated from the DB, versioned per release.
- Lookup tables: ItemID ↔ name ↔ expansion ↔ category; BodyID ↔ mobile ↔ taxonomy.
- Build automation: one command regenerates DB → datasets → site data files; catalog pages become generated artifacts, not hand-maintained markdown.
- The catalog's 31k pages enter the search index via the structured layer.

**Acceptance:** rebuilding from scratch produces byte-identical datasets; no page content lives only in markdown that the DB can't regenerate.

**Dependencies:** Stages 1–2. The old roadmap's Phases 5–6 (exporters, markdown parser, validators, JSON/CSV generators) all live here.

## Stage 4 — Search & discovery

**Goal:** fast discovery over structured data, not grep over markdown.

**Deliverables:**
- Site search v2 backed by the datasets: full-text + faceted (expansion, category, era, facet).
- ID lookups: ItemID, BodyID, hue/art index.
- Mobile search by taxonomy (family, fame/karma range, expansion).
- Search index generated at build time from Stage 3 datasets.

**Acceptance:** sub-100ms queries client-side; every entity reachable by ID and by name.

**Dependencies:** Stage 3. (The current site's search and hex-ID lookup are the v1 prototype this replaces.)

## Stage 5 — AI-ready knowledge system (RAG)

**Goal:** the corpus is ingestible by an LLM with provenance, not scraped HTML.

**Deliverables:**
- Chunking rules: per page type (lore = semantic sections; items = one chunk per entity + metadata block; mechanics = rule-level chunks). Cross-links preserved as chunk metadata.
- Metadata enrichment on chunks: entity IDs, expansion, era, confidence labels (Canon vs. community recollection — the wiki's existing convention).
- Embedding pipeline: local-first (Ollama) for iteration; reproducible config.
- Vector store: one collection (Qdrant vs. Chroma — evaluate at this stage, not before).
- Query evaluation set: lore questions, item lookups, mobile lookups, expansion history, shard history — with expected answers from the corpus.

**Acceptance:** the eval set answers correctly with citations to chunk IDs; ingestion re-runs from Stage 3 datasets.

**Dependencies:** Stage 3 (chunking consumes datasets, not raw markdown). Stage 4's taxonomy powers faceted retrieval filters.

## Stage 6 — Sentient World integration

**Goal:** the knowledge system drives living NPCs and dynamic storytelling — the long-term vision.

**Deliverables:**
- Query endpoints: NPCs ask lore / locations / items / factions questions against the RAG layer.
- World memory: faction state, historical references resolvable to corpus chunks.
- Quest-generation hooks: seeded from lore entities with provenance back to articles.

**Acceptance:** an NPC can answer "who was Mondain" and "what happened at Trinsic" with citations; quest seeds trace to corpus entities.

**Dependencies:** Stage 5. This is the only stage that should be thinking about NPCs — everything before it is infrastructure.

## Cross-cutting: engineering standards

- **Repo layout:** `content/` (markdown + front matter), `schema/`, `taxonomy/`, `datasets/` (generated, versioned), `site/` (built from datasets), `pipelines/` (exporters, validators, builders). Generated files are never hand-edited.
- **Releases:** dataset + site releases versioned together (e.g., `v2026.10`); changelog per release.
- **CI checks:** markdown link check (already in place), metadata validator (Stage 1), build reproducibility check (Stage 3), missing-image report (Stage 2).
- **Conventions (carried over):** Canon/Non-Canon labels on lore pages only; sources as simple bottom-of-page lists; uncertain facts hedged as community recollection.

## 30-day plan

- **Week 1:** Lock metadata schema v1. Write item + mobile templates. Publish `taxonomy.yaml`. (Stage 1 core — unblocks everything.)
- **Week 2:** Confirm the LFS asset push landed. Build the export pipeline. First 1,000 item thumbnails through it.
- **Week 3:** First 500 mobile thumbnails (representative idle frames). Wire image paths into front matter. Missing-image report live.
- **Week 4:** SQLite source of truth stood up; first JSON catalogs generated; metadata validator passing; RAG ingestion pipeline designed against the datasets.

## Critical path

```
Stable IDs (done) → Metadata schema → Asset pipeline → Dataset builds → Search → RAG
```

Same five pieces as before, but the first is already behind us, and "metadata schema" is now explicitly the gating item — not another content batch.

## Open decisions

1. **Vector store:** Qdrant vs. Chroma — defer to Stage 5; evaluate with the real eval set, not on vibes.
2. **UOAssetSuite's role:** it's a WPF GUI app today. As the automation exporter it needs a headless/CLI or batch mode — either extend it or keep exporters as standalone scripts in `pipelines/`. Decide in Stage 2.
3. **Thumbnail hosting:** private asset-db repo (LFS) is the plan; confirm the public site's image URL scheme before Week 3.
4. **Catalog regeneration:** 31k catalog pages become build artifacts in Stage 3 — confirm you're comfortable with the repo diff churn that implies, or keep generated pages on a separate branch.
